# Спецификация проекта: Генератор шаблонов заявок (Transactioner)

## Описание
Простое кроссплатформенное приложение для создания шаблонов заявок на депозиты и выводы в покер-румах. Предназначено для стандартизации процесса и снижения количества ошибок из-за невнимательности при ручном заполнении данных сотрудниками.

- **[РЕШЕНО]** Режим подключения серверной версии: Supabase является главным источником данных; добавление и редактирование требуют подключения к интернету; без сети доступен только просмотр последней успешно синхронизированной локальной копии.
- **[РЕШЕНО]** Совместимость с сайтом: сущности `player` и `room` получают собственные стабильные UUID в Transactioner; будущие сущности сайта связываются через отдельные таблицы внешних идентификаторов и не определяют структуру основной БД.
- **[РЕШЕНО]** Первая серверная версия не сохраняет историю сформированных депозитов/выводов. Она хранит только необходимые данные игроков/румов и аудит изменений; полноценная сущность операции откладывается до появления подтверждённого рабочего сценария.
- **[РЕШЕНО]** Кошельки игрока проектируются отдельной сущностью `player_wallets`, а не полями внутри `players`. История начинает накапливаться с первого дня серверной версии: заменённые кошельки архивируются, даже если отдельный экран истории пока отсутствует.
- **[РЕШЕНО]** Сотрудники используют Google Workspace с собственным корпоративным доменом. Разрешённый домен задаётся в защищённой серверной конфигурации и не зашивается в десктопное приложение.
- **[РЕШЕНО]** Корпоративного домена недостаточно для входа: доступ к Transactioner получает только рабочий адрес, заранее разрешённый администратором. Разрешение можно отозвать без удаления истории действий сотрудника.
- **[РЕШЕНО]** В первой серверной версии две роли сотрудников: `admin` и `operator`. Роль только для чтения не входит в первый релиз, но модель допускает добавление новых ролей позже.
- **[РЕШЕНО]** `operator` может редактировать общий справочник румов, условия сделок, депозитные кошельки и общие справочные материалы. Все такие изменения версионируются или попадают в аудит, чтобы ошибку можно было найти и откатить.
- **[ПЛАН]** Справочная модель строится как `knowledge_documents` → упорядоченные `knowledge_sections` → история версий. Она поддерживает отдельные документы с полной информацией, сделками, шаблонами проверки привязки, быстрыми ответами и общие/привязанные к руму материалы.
- **[ПЛАН]** Будущая автоматизация проверки привязки сначала атомарно сохраняет игрока и аккаунт в Supabase, затем ставит отдельное задание на экспорт в Google/Notion. Внешний сервис не участвует в основной транзакции сохранения игрока.
- **[РЕШЕНО]** Первая версия Supabase не объединяется с Google Docs или Notion. Провайдер будущей интеграции пока не выбран; внутренняя модель и контракт адаптера не должны зависеть от конкретного сервиса.
- **[РЕШЕНО]** Справочные документы не требуют одновременного посимвольного редактирования как в Google Docs. Первая версия использует обычное сохранение, историю версий и проверку ревизии, чтобы устаревшая форма не перезаписала чужое изменение.
- **[РЕШЕНО]** Вложения и загрузка изображений не входят в первую серверную версию: случайные скриншоты в исходных документах редки и некритичны. Модель разделов допускает будущее добавление `knowledge_attachments` без изменения существующего контента.
- **[РЕШЕНО]** Начальное наполнение Supabase охватывает весь существующий на момент миграции набор документов по румам и ещё несколько новых румов, а не только Champion Poker, Nexa и RedStar. Частичный пилот не должен стать окончательным источником неполных данных.
- **[РЕШЕНО]** Ожидаемый объём начальной миграции — около 50 документов. Ручное копирование каждого раздела не используется как основной способ; нужен одноразовый повторяемый импорт через staging и ручную проверку перед публикацией.
- **[РЕШЕНО]** Документы с полной информацией по румам в основном используют общий каркас заголовков. Импорт сопоставляет их со стабильными смысловыми ключами; номера, порядок, отсутствующие необязательные разделы и небольшие различия заголовков не должны ломать перенос.
- **[РЕШЕНО]** Внутренний `room_guide` не имеет языковых версий: он примерно на 99% русский и может содержать отдельные английские термины. Сделки и шаблоны сообщений по проверке привязки локализуются отдельно на `RU`, `EN`, `ES`.
- **[РЕШЕНО]** У проверки привязки два разных типа шаблонов: `verification_request` — запрос сотрудника руму на проверку, и `verification_response` — сообщение игроку после получения результата. Это отдельные логические шаблоны и отдельные записи, а не две локализации или две части одного шаблона. Существующая функция реализует только первый тип.
- **[РЕШЕНО]** `verification_response` первой версии хранится как полный готовый текст для конкретной комбинации рум / тип сделки / результат / язык. Ответ не собирается из бонуса, вейджера и других структурированных блоков; плейсхолдеры в ответе игроку пока не используются.
- **[РЕШЕНО]** Будущий переход проверки привязки в статус `ok` атомарно сохраняет точную версию полного текста ответа, возвращает её приложению для копирования и создаёт отдельное задание синхронизации статуса с Google Docs или Notion, если такой адаптер будет подключён.
- **[РЕШЕНО]** Telegram-анонс создаётся только после одновременного выполнения двух условий: проверка аккаунта имеет статус `ok`, а у игрока есть активный кошелёк с назначением `rakeback_payout`. Кошелёк для обычного вывода это условие не выполняет. Все подтверждённые и ещё не переданные аккаунты одного игрока объединяются в одно сообщение; каждый аккаунт включается в такой анонс не более одного раза.
- **[РЕШЕНО]** Первый сохранённый рейкбек-кошелёк игрока становится основным. При постоянной замене старый кошелёк архивируется, а новый становится основным с сохранением истории. Кошелёк, указанный игроком только для одной выплаты, не сохраняется в `player_wallets`, не заменяет основной и не выполняет условие Telegram-анонса.
- **[РЕШЕНО]** Telegram-анонс новых аккаунтов формируется из структурированных данных, а не хранится отдельным полным текстом для каждого рума. Для каждого аккаунта выводятся рум, идентификаторы и снимок сделки; основной рейкбек-кошелёк и контакты игрока добавляются один раз в конце общего сообщения.
- **[РЕШЕНО]** Условия новых аккаунтов и постоянной смены рейкбек-кошелька автоматически создают только серверный черновик Telegram-сообщения. Отправка возможна исключительно после обязательного предпросмотра и явного нажатия сотрудником кнопки `Отправить`.
- **[РЕШЕНО]** Оба автоматических типа Telegram-сообщений отправляются в один общий рабочий чат. В первой версии сотрудник не выбирает адресата: `chat_id` и необязательный ID темы задаются только в защищённой серверной конфигурации.
- **[РЕШЕНО]** В предпросмотре можно изменить каждое поле содержимого, отменить сообщение или отложить его. Быстрый перенос по умолчанию — 15 минут; сотрудник может выбрать другое время. По окончании переноса черновик снова появляется для проверки, но никогда не отправляется автоматически.
- **[РЕШЕНО]** Исправления username, идентификаторов аккаунта, сделки, кошелька и контактов в предпросмотре не являются разовой правкой текста: они сохраняются в соответствующих основных сущностях БД. После сохранения сервер заново строит черновик из актуальных данных, чтобы карточка игрока, история изменений и сообщение в рабочем чате не расходились.
- **[РЕШЕНО]** Обычный путь не требует отдельного сохранения: если предпросмотр верен, сотрудник сразу нажимает `Отправить`. Если поля были исправлены, `Отправить` одной серверной операцией сохраняет исправления в БД и ставит зафиксированный текст в очередь. Отдельная кнопка `Сохранить изменения` нужна только для редкого случая, когда данные следует исправить, а сообщение затем отложить или отменить.
- **[РЕШЕНО]** Если одновременно работают несколько сотрудников, приоритет на продолжение отложенного черновика получает сотрудник, который последним содержательно с ним работал. Задача остаётся в общей серверной очереди и переходит коллегам, если приоритетный сотрудник недоступен или не продолжил работу за ограниченное время.
- **[НЕ ВХОДИТ]** Произвольные сообщения из приложения не реализуются: сотрудник отправляет их непосредственно в Telegram, где уже доступны привычные редактирование и удаление.
- **[ОТЛОЖЕНО]** Специальное структурированное сообщение `deal_changed` пока не входит в первую реализацию: случай редкий и может отправляться сотрудником непосредственно в Telegram. История сделки аккаунта при этом остаётся частью целевой модели.
- **[ОЖИДАЕТ]** Сборка финального дистрибутива (.dmg / .exe).

## Пользовательский путь (User Flow)
1. Сотрудник вводит/вставляет **юзернейм игрока из мессенджера** или часть любого сохраненного контакта/номера.
2. Приложение делает поиск по локальной базе данных и отображает **список покер-румов**, в которых у данного игрока зарегистрированы аккаунты.
3. Сотрудник выбирает нужный рум из предложенного списка.
4. Выбирается тип операции: **Депозит** или **Вывод**.
5. В зависимости от выбора открывается **форма для заполнения**. Известные данные (например, юзернейм в руме, Player ID, контакт, кошелек и сеть/монета по умолчанию для вывода) подтягиваются из базы автоматически.
6. Система генерирует **готовый шаблон заявки** в текстовом формате и предоставляет кнопку **Скопировать**.
7. Если при выводе сотрудник вводит кошелек или сеть/монету, отличающиеся от сохраненных в профиле игрока, приложение предлагает заменить значения по умолчанию.

## Технические детали и требования
*(В процессе уточнения с заказчиком)*
* **Платформа:** Кроссплатформенное десктопное приложение.
* **Каналы общения с игроками:** Telegram, WhatsApp, Discord, Teams, Email.
* **Стек:** Electron, React, TypeScript, TailwindCSS, Vite, **SQLite (локальная БД)**
* **База данных:** Хранение связок "Игрок -> несколько контактов/мессенджеров -> доступные аккаунты в покер-румах", а также кошелька и сети/монеты по умолчанию для выводов. Ожидаемый объем: до нескольких сотен игроков.
* **Уникальность контактов:** Повторное добавление той же пары "канал связи + юзернейм/номер" запрещено, чтобы новые данные не перезаписывали существующую карточку.
* **Список покер-румов:** Nexa, Champion Poker, RedStar

## Планируемая серверная версия: источник данных и офлайн-режим

Supabase является главным источником данных серверной версии. Локальная SQLite-БД больше не считается независимым источником истины и используется только как кеш последней успешно полученной версии данных.

Зафиксированное поведение:
* поиск, добавление и редактирование при наличии сети работают с актуальными данными Supabase;
* создание, изменение, объединение и удаление сущностей без подключения к серверу запрещены;
* при потере сети приложение может показать последнюю успешно синхронизированную локальную копию в режиме только для чтения;
* интерфейс явно показывает офлайн-режим и время последней успешной синхронизации, чтобы сотрудник не принял устаревшие данные за актуальные;
* после восстановления соединения приложение обновляет кеш с сервера, а не пытается отправить очередь локальных изменений;
* полноценная офлайн-синхронизация с разрешением конфликтов не входит в первую серверную версию.

Точный состав данных, разрешённых для локального кеширования, и требования к защите кеша на устройстве будут определены отдельно до реализации.

## Планируемая серверная версия: совместимость с сущностями сайта

Transactioner не ожидает готовности или окончательной схемы сайта. В Supabase создаются собственные канонические сущности `players` и `rooms` со стабильными UUID. Каноническая сущность — это основная запись внутри Transactioner, на которую ссылаются остальные таблицы приложения.

Зафиксированные правила:
* внутренние UUID Transactioner не зависят от названия рума, email, мессенджера или ID сторонней системы;
* ID сайта, Directus, Google, Notion и других систем не используются как primary key таблиц Transactioner;
* соответствия внешним системам хранятся отдельно, поэтому отсутствие интеграции не блокирует развитие приложения;
* получение схемы сайта в будущем приводит к добавлению адаптера и записей соответствия, а не к переделке основных сущностей;
* автоматическое объединение игроков только по имени, нику, email или мессенджеру запрещено;
* спорные совпадения отправляются на ручное подтверждение;
* ошибочную связь с внешней сущностью можно отменить без удаления локального игрока или рума;
* первая интеграция с сайтом должна быть односторонней и read-only до согласования владельца каждого поля.

Предварительная схема внешних идентификаторов:

```text
players / rooms
      │ 1
      │
      │ N
      ▼
external_entity_refs
┌──────────────────────────────┐
│ id UUID PK                   │
│ provider TEXT                │  website / directus / google / notion
│ entity_type TEXT             │  player / room
│ external_id TEXT             │
│ local_entity_id UUID         │
│ external_revision TEXT       │
│ status TEXT                  │  candidate / linked / inactive / conflict
│ linked_by UUID               │
│ linked_at TIMESTAMPTZ        │
└──────────────────────────────┘

UNIQUE(provider, entity_type, external_id)
```

При появлении схемы сайта отдельный контракт должен описать поля `Player` и `Room`, владельца каждого поля, правила сопоставления, конфликты, удаление, повторную доставку событий и откат ошибочного объединения.

## Планируемая серверная версия: операции и кошельки игроков

Первая серверная версия остается генератором рабочих шаблонов и не создает отдельную запись для каждого депозита или вывода. В Supabase не сохраняются сумма, TX и статус каждой сформированной заявки. Это уменьшает объем чувствительных финансовых данных и не вводит неподтвержденный процесс ведения операций.

При этом административные и пользовательские изменения сущностей сохраняются в `audit_log`: кто, когда и какие данные игрока, аккаунта, рума или кошелька изменил.

Текущие поля SQLite `players.default_wallet` и `players.default_wallet_network` не переносятся в таком виде в целевую схему. В Supabase кошелек становится отдельной сущностью:

```text
players
┌──────────────────────┐
│ id UUID PK           │
└──────────┬───────────┘
           │ 1
           │
           │ N
           ▼
player_wallets
┌──────────────────────────────┐
│ id UUID PK                   │
│ player_id UUID FK            │
│ purpose TEXT                 │  rakeback_payout / room_withdrawal
│ payment_system TEXT          │  crypto / Skrill / ...
│ currency TEXT NULL           │  USDT / USDC / ...
│ network TEXT NULL            │
│ address TEXT                 │
│ memo_tag TEXT                │
│ label TEXT                   │
│ is_default BOOLEAN           │
│ status TEXT                  │  active / archived
│ created_at TIMESTAMPTZ       │
│ created_by UUID FK           │
│ archived_at TIMESTAMPTZ      │
│ archived_by UUID FK          │
│ superseded_by UUID FK        │
└──────────────────────────────┘
```

Правила модели:
* у игрока может быть несколько кошельков;
* назначение кошелька хранится явно в `purpose`; значение не выводится из названия, сети или последней операции;
* `rakeback_payout` используется для дополнительных выплат рейкбека, а `room_withdrawal` — как сохранённое направление обычного вывода игрока;
* кошелёк `room_withdrawal` никогда не выполняет условие Telegram-анонса автоматически;
* рейкбек-кошелёк принадлежит игроку и может использоваться для его последующих регистраций в других румах;
* первый сохранённый кошелёк `rakeback_payout` автоматически становится основным;
* у игрока одновременно существует только один активный основной кошелёк `rakeback_payout`;
* постоянная замена выполняется одной транзакцией: создаётся новый основной кошелёк, прежний архивируется и получает ссылку `superseded_by` на новый;
* разовый адрес для конкретной выплаты существует только в текущей форме/шаблоне, не записывается в `player_wallets` и не меняет основной кошелёк;
* если в будущем появится история финансовых операций, разовый адрес может сохраняться только снимком внутри конкретной операции, но не как кошелёк игрока по умолчанию;
* замена кошелька не требует изменения записи `players`;
* обычный интерфейс первой версии запрашивает только активные кошельки;
* будущий экран истории сможет запросить активные и архивные записи без изменения основной схемы;
* доступ к адресам кошельков и их истории ограничивается политиками Supabase RLS и отражается в аудите;
* накопление архивных записей начинается с первого дня работы серверной версии;
* пока экран истории не реализован, обычный интерфейс не показывает архивные записи, но они остаются доступными для будущей функции и административного аудита.

Интерфейс не пытается угадать намерение по отличающемуся адресу. Для нового адреса сотрудник явно выбирает одно из двух действий: `Заменить основной рейкбек-кошелёк` или `Использовать один раз без сохранения`. Это защищает основной кошелёк от случайной замены.

В коде доступ к кошелькам должен идти через отдельный модуль/репозиторий, а не через прямое чтение полей игрока. Первая версия использует операции получения активных кошельков по назначению и установки кошелька по умолчанию для конкретного назначения; получение полной истории можно добавить в тот же контракт позже.

## Планируемая серверная версия: расширяемые справочники

Показанная структура Google Docs состоит не из одного однородного текста, а из логического документа и упорядоченных разделов. В документе рума видны разделы вроде общего описания, шаблона сделки, ссылок, перепривязки аккаунта, верификации, бонуса на первый депозит, платежных систем, рейка, рейкбека, вспомогательного софта, особенностей и информации о трафике.

Внутренняя модель не копирует Google Docs целиком одним текстовым полем. Она хранит документ как набор небольших смысловых разделов со стабильными ключами. Название раздела можно изменить без потери его идентичности или связи с будущим адаптером.

Поддерживаются отдельные логические документы:
* полная информация о конкретном руме;
* сделки и условия;
* шаблоны ответов и запросов для проверки привязки;
* общие и привязанные к руму быстрые ответы;
* будущие FAQ, инструкции и заметки.

```text
rooms
┌──────────────────────┐
│ id UUID PK           │
└──────────┬───────────┘
           │ 0..N
           │
           │ N
           ▼
knowledge_documents
┌──────────────────────────────┐
│ id UUID PK                   │
│ room_id UUID FK NULL         │  NULL = общий материал
│ document_key TEXT            │
│ document_kind TEXT           │  room_guide / deals / link_verification / quick_answers
│ title TEXT                   │
│ status TEXT                  │  draft / published / archived
│ revision INTEGER             │
│ created_by / updated_by UUID │
│ created_at / updated_at      │
└──────────┬───────────────────┘
           │ 1
           │
           │ N
           ▼
knowledge_sections
┌──────────────────────────────┐
│ id UUID PK                   │
│ document_id UUID FK          │
│ parent_section_id UUID NULL  │
│ section_key TEXT             │  стабильный ключ, не заголовок
│ section_kind TEXT            │  rich_text / quick_reply / structured_block
│ title TEXT                   │
│ language TEXT                │
│ position INTEGER             │
│ content_format TEXT          │  plain / markdown / canonical_rich_text
│ content JSONB                │
│ searchable_text TEXT         │
│ metadata JSONB               │
│ status TEXT                  │  draft / published / archived
│ revision INTEGER             │
│ created_by / updated_by UUID │
│ created_at / updated_at      │
└──────────┬───────────────────┘
           │ 1
           │
           │ N
           ▼
knowledge_section_versions
┌──────────────────────────────┐
│ id UUID PK                   │
│ knowledge_section_id UUID FK │
│ version INTEGER              │
│ snapshot JSONB               │
│ changed_by UUID FK           │
│ changed_at TIMESTAMPTZ       │
└──────────────────────────────┘
```

Справочник остаётся гибридным:
* длинные описания, инструкции, FAQ и быстрые ответы хранятся разделами документа;
* кошельки, сделки, платежные методы, страны и шаблоны проверки привязки остаются отдельными типизированными таблицами с настоящими ограничениями БД;
* `structured_block` не дублирует кошелек или сделку внутри JSON, а указывает интерфейсу показать соответствующий типизированный блок для выбранного рума;
* новая разновидность обычного текстового материала добавляется без изменения схемы;
* новая сложная бизнес-сущность с собственными правилами получает отдельную таблицу и отдельный компонент, а не прячется в универсальном JSON;
* `room_id = NULL` используется для общих документов и быстрых ответов;
* порядок разделов хранится явно и может редактироваться перетаскиванием;
* любой активный `operator` или `admin` может менять любой справочный документ;
* каждое сохранение увеличивает `revision`, записывает автора и создаёт версию для просмотра и отката;
* при сохранении устаревшей ревизии сервер не перезаписывает чужое изменение молча, а возвращает конфликт;
* при конфликте интерфейс показывает актуальную серверную версию и несохранённый вариант сотрудника, чтобы пользователь мог сравнить их и повторить изменение;
* синхронное отображение курсоров и посимвольных изменений других сотрудников не входит в первую версию;
* API чтения поддерживает фильтры по документу, руму, типу раздела, языку, статусу и поисковой строке.

Редактор первой версии поддерживает обычный текст, заголовки, списки, выделение и безопасные ссылки. Произвольный HTML не хранится и не выполняется. Изображения и файлы не загружаются в Supabase Storage на первом этапе.

Если вложения понадобятся позже, добавляется независимая связь, не меняющая `knowledge_documents` и `knowledge_sections`:

```text
knowledge_attachments
┌──────────────────────────────┐
│ id UUID PK                   │
│ knowledge_section_id UUID FK │
│ storage_path TEXT            │
│ file_name TEXT               │
│ mime_type TEXT               │
│ size_bytes BIGINT            │
│ alt_text TEXT                │
│ created_by UUID FK           │
│ created_at TIMESTAMPTZ       │
└──────────────────────────────┘
```

Будущий импорт из Google Docs/Notion может либо перенести поддерживаемое изображение в Supabase Storage, либо пометить неподдерживаемое вложение в отчёте импорта. Отсутствие картинки не должно блокировать импорт остальных разделов.

### Начальная миграция справочника

Перед запуском серверной версии проводится инвентаризация всех существующих документов и разделов. Для каждого документа фиксируются рум, назначение, язык, текущий владелец, дата актуальности и соответствие внутреннему `document_kind`.

Начальная миграция должна:
* охватить все актуальные документы, существующие к моменту перехода, плюс несколько новых румов;
* не ограничиваться тремя румами из текущего локального seed;
* создать стабильные UUID и ключи документов/разделов до возможной интеграции с Google или Notion;
* сформировать отчёт о пропущенных, пустых и неоднозначных разделах;
* пройти ручную проверку количества документов и ключевых операционных данных после импорта;
* быть повторяемой на тестовом проекте Supabase без создания дублей.

Ожидаемый объём — около 50 документов. Поэтому основной путь — одноразовый полуавтоматический импорт из заранее экспортированных файлов или нормализованного промежуточного формата. Ручной ввод используется только для исправления неоднозначных разделов. Такой инструмент является миграцией, а не постоянной Google API-интеграцией.

```text
Экспорт примерно 50 исходных документов
                  │
                  ▼
Вычисление checksum + регистрация import batch
                  │
                  ▼
Разбор заголовков, порядка и содержимого
                  │
                  ▼
Staging documents / sections
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
  валидные разделы     ошибки и неоднозначности
        │                   │
        └─────────┬─────────┘
                  ▼
Предпросмотр: что создастся, изменится или пропустится
                  │
                  ▼
Ручное подтверждение ответственного сотрудника
                  │
                  ▼
Одна публикация в knowledge_* и типизированные таблицы
                  │
                  ▼
Отчёт: импортировано / исправить / пропущено
```

Требования к инструменту начальной миграции:
* исходные файлы сначала попадают во временный staging, а не напрямую в рабочие таблицы;
* повторный запуск одного и того же import batch определяется по checksum и не создаёт дубли;
* заголовки сопоставляются со стабильными `section_key`, а не становятся идентификаторами сами по себе;
* сделки, платежные методы и шаблоны привязки извлекаются в типизированные сущности только после успешной валидации;
* неизвестный раздел сохраняется как текстовый раздел или отмечается для ручного сопоставления, но не теряется;
* перед публикацией показываются количества документов, разделов, ошибок и различий;
* публикация либо завершается целиком для выбранного batch, либо откатывается;
* результат можно проверить на отдельном тестовом проекте Supabase до переноса в рабочую базу.

Для документов типа `room_guide` используется стартовый профиль разделов:

| Возможный заголовок | Канонический `section_key` | Обязательность |
|---|---|---|
| Краткое общее описание | `general_summary` | основной |
| Краткая информация | `quick_facts` | основной |
| Шаблон сделки | `deal_template` | основной |
| Ссылки / загрузка клиента | `download_links` | основной |
| Перепривязка аккаунта | `account_relinking` | необязательный |
| Верификация | `verification` | необязательный |
| Бонус на первый депозит | `first_deposit_bonus` | необязательный |
| Платежные системы | `payment_systems` | основной |
| Рейк | `rake` | необязательный |
| Рейкбек + Акции | `rakeback_promotions` | необязательный |
| Вспомогательный софт | `supporting_software` | необязательный |
| Особенности | `special_notes` | необязательный |
| Информация о трафике | `traffic` | необязательный |
| Доступные страны | `available_countries` | необязательный |
| Ответы на вопросы | `faq` | необязательный |

Правила распознавания этого профиля:
* ведущий номер и точка удаляются до сопоставления;
* регистр, повторные пробелы и несущественная пунктуация игнорируются;
* для известных вариантов написания поддерживается явный список алиасов;
* номер раздела используется только для исходного порядка и не определяет его смысл;
* отсутствующий необязательный раздел не является ошибкой;
* неизвестный заголовок сохраняется как отдельный текстовый раздел и попадает в отчёт на проверку;
* два раздела, распознанные как один `section_key`, считаются конфликтом и требуют ручного решения;
* отдельные документы со сделками и шаблонами привязки получают собственные профили разбора после изучения их фактической структуры.

Для будущего Google/Notion-адаптера связи хранятся отдельно:

```text
external_content_bindings
┌─────────────────────────────────┐
│ id UUID PK                      │
│ provider TEXT                   │  google_docs / notion
│ local_document_id UUID FK       │
│ local_section_id UUID FK NULL   │
│ external_document_id TEXT       │
│ external_tab_or_page_id TEXT    │
│ external_block_id TEXT NULL     │
│ external_revision TEXT          │
│ sync_direction TEXT             │  import / export
│ status TEXT                     │
│ last_synced_at TIMESTAMPTZ      │
└─────────────────────────────────┘
```

Первая версия Supabase не создаёт эти внешние связи и не выбирает между Google Docs и Notion. Когда решение будет принято, адаптер сопоставит внешний документ и его разделы с уже существующими стабильными UUID/ключами. Одни и те же данные не должны одновременно свободно редактироваться в двух системах: для каждой категории перед интеграцией назначается один источник истины.

### Языковая модель справочников и шаблонов

Внутренний документ `room_guide` хранится в одном экземпляре. Его `default_language = 'ru'`, а `localization_mode = 'none'`. Отдельные английские названия, термины и ссылки внутри русского раздела не создают английскую версию документа.

Сделки и шаблоны сообщений имеют стабильную неязыковую сущность и связанные локализации. Это не три независимых шаблона: это один логический шаблон с версиями `ru`, `en`, `es`.

```text
│ purpose TEXT             │       │ label TEXT                 │
│ outcome TEXT NULL        │       │ subject TEXT NULL          │

```

Ограничения:
* `UNIQUE(room_deal_id, locale)` не допускает две активные версии одной сделки на одном языке;
* `UNIQUE(template_id, locale)` делает то же для шаблонов привязки;
* допустимые локали первой версии: `ru`, `en`, `es`;
* статус готовности хранится отдельно для каждой локализации, чтобы незавершённый перевод не считался опубликованным;
* английские фрагменты внутри русского `room_guide` импортируются как часть исходного текста и не переводятся автоматически;
* машинный перевод не публикуется без ручной проверки сотрудником.

### Два типа шаблонов проверки привязки

`verification_request` используется сотрудником для обращения к представителю рума или аффилейта. Сюда мигрируют существующие `link_verification_templates` приложения: получатель, канал, тема, тело запроса и нужные идентификаторы игрока.

`verification_response` — другой логический шаблон, который отправляется игроку после получения результата. Он не является продолжением, переводом или автоматически изменённой версией `verification_request`.

#### Полный текст ответа в первой версии

Каждая локализация `verification_response` хранит полный готовый текст сообщения игроку. Даже если ответы разных румов частично повторяются, приложение не собирает их во время выполнения из бонуса, вейджера, промокода, разделов справочника или других структурированных блоков. Разный состав и порядок информации в румах остаётся частью конкретного текста.

```text
verification_response
  ├── room
  ├── deal_type
  ├── outcome
  ├── locale
  ├── version
  └── complete body ready to copy
```

Плейсхолдеры в ответах игроку не входят в первую версию. Если позже ручное обновление повторяющихся условий станет реальной проблемой, централизованные поля сделки и подстановки добавляются отдельным решением без изменения уже сохранённых полных текстов.

Правила шаблонов:
* `purpose` принимает минимум `verification_request` и `verification_response`;
* запрос и ответ всегда хранятся как разные записи с разными `template_key`; общими у них могут быть только рум и тип сделки;
* `outcome` используется только для ответа игроку и позволяет иметь разные варианты результата;
* `deal_type` необязателен и отличает ответы для разных вариантов сделки одного рума;
* каждая локализация `ru/en/es` редактируется и публикуется независимо;
* `verification_request` может продолжать использовать существующий ограниченный набор плейсхолдеров с данными запроса;
* поле `body` ответа обязательно и содержит весь текст, готовый к копированию без подстановок;
* отсутствие опубликованного текста для выбранных `room / deal_type / outcome / locale` является явной ошибкой; похожий шаблон не выбирается молча;
* при переводе проверки в результирующий статус сохраняются ID локализации, её версия и снимок полного текста, чтобы последующее редактирование шаблона не меняло уже выданный ответ задним числом.

## Будущий этап: проверка привязки и автоматизации

Текущий код уже содержит признак `persistPlayerInMainDb` в правилах румов, но экран проверки привязки пока не вызывает `savePlayer`. Статус `Check / Ok / Denied / Retag` существует только в форме и попадает в TSV; отдельной записи проверки, истории статусов и Telegram-интеграции сейчас нет.

### Операционная сущность проверки

Шаблон и конкретная проверка являются разными сущностями. `link_verification_templates` хранит переиспользуемые тексты, а `link_verifications` — один рабочий процесс проверки конкретного аккаунта игрока в руме.

```text
link_verifications
┌────────────────────────────────────┐
│ id UUID PK                         │
│ player_room_account_id UUID FK     │
│ status TEXT                        │  check / ok / denied / retag
│ requested_at / requested_by        │
│ resolved_at / resolved_by          │
│ response_localization_id UUID NULL │
│ response_version INTEGER NULL      │
│ response_text_snapshot TEXT NULL   │
│ external_revision TEXT NULL        │
│ created_at / updated_at            │
└────────────────────────────────────┘
```

Внутренние статусы хранятся в нижнем регистре. Написание `Ok`, `OK` или другое представление во внешнем документе преобразуется адаптером и не меняет внутренний набор значений.

Игрок и `player_room_account` сохраняются независимо от наличия рейкбек-кошелька. Отсутствие кошелька задерживает только Telegram-анонс, но не потерю подтверждённого аккаунта и не выдачу ответа игроку.

### Переход проверки в `ok`

```text
Сотрудник выбирает проверку и ставит status = ok
                         │
                         ▼
Сервер проверяет текущую ревизию и опубликованный
полный verification_response нужного языка
                         │
                         ▼
Одна транзакция Supabase
  ├── изменить link_verification.status на ok
  ├── сохранить ID + version локализации ответа
  ├── сохранить snapshot полного response_text
  ├── создать integration_outbox для Google/Notion
  └── проверить готовность Telegram-анонса
                         │
                         ▼
API возвращает сохранённый response_text
                         │
                         ▼
Приложение показывает текст и кнопку «Скопировать»
                         │
                         ▼
Worker независимо синхронизирует внешний документ
```

Supabase остаётся главным источником состояния: действие сначала фиксируется в БД, а Google Docs или Notion обновляется через адаптер. Поэтому недоступность внешнего сервиса не отменяет `ok` и не блокирует копирование ответа; сотрудник видит отдельный статус синхронизации и может повторить её позже. Если в будущем разрешаются ручные изменения статуса во внешнем документе, импорт-адаптер вызывает тот же серверный переход, а не реализует параллельную бизнес-логику.

Основные гарантии:
* статус `ok` и снимок ответа сохраняются атомарно;
* повтор того же перехода возвращает уже сохранённый текст и не создаёт повторные задания;
* внешний адаптер получает сохранённое состояние, а не заново сформированный текст;
* адаптеры Google и Notion используют один версионированный внутренний контракт;
* статусы, отличные от `ok`, не запускают положительный ответ или Telegram-анонс;
* первая серверная версия создаёт необходимые сущности и границы модулей, но не реализует Google/Notion API.

### Telegram-сообщения рабочего чата

Система поддерживает разные бизнес-события через одну очередь доставки:

* `new_accounts` — один или несколько подтверждённых аккаунтов игрока, для которого уже есть основной рейкбек-кошелёк;
* `rakeback_wallet_changed` — постоянная замена основного рейкбек-кошелька игрока;
* `deal_changed` — зарезервированный будущий тип для изменения сделки аккаунта.

Первое сохранение рейкбек-кошелька не считается его сменой, а разовый адрес не создаёт `rakeback_wallet_changed`. Первоначальное назначение сделки при регистрации не считается `deal_changed`.

Оба автоматических типа первой версии используют одно назначение `destination_key = 'operations_chat'`. Его Telegram `chat_id` и необязательный `message_thread_id` хранятся в серверной конфигурации или защищённой системной настройке. Десктопное приложение не получает эти значения и не показывает выбор чата.

#### Анонс новых аккаунтов

Анонс относится к набору готовых `player_room_account` одного игрока. Для включения каждого аккаунта одновременно должны выполняться условия:

1. связанная проверка имеет статус `ok`;
2. у этого игрока существует активный основной `player_wallet` с `purpose = 'rakeback_payout'` и `is_default = true`;
3. этот аккаунт ещё не был включён в успешно созданное задание `new_accounts` для выбранного рабочего чата; при ошибке повторяется то же задание, а не создаётся новое.

Кошелёк с `purpose = 'room_withdrawal'` и разовый адрес условие не выполняют. Проверка готовности запускается после любого из двух событий: перехода проверки в `ok` и сохранения/замены основного рейкбек-кошелька. Поэтому поддерживаются оба порядка:

```text
Сценарий A                            Сценарий B
verification = ok                    rakeback wallet уже есть
rakeback wallet отсутствует          verification ещё не ok
          │                                     │
          ▼                                     ▼
ждём сохранения кошелька              ждём результата проверки
          │                                     │
          └──────────────┬──────────────────────┘
                         ▼
          оба условия выполнены одновременно
                         │
                         ▼
       создать один серверный draft со всеми
       готовыми аккаунтами этого игрока
                         │
                         ▼
        обязательный preview перед отправкой
```

```text
telegram_notification_tasks
┌────────────────────────────────────┐
│ id UUID PK                         │
│ event_type TEXT                    │  new_accounts /
│                                    │  rakeback_wallet_changed /
│                                    │  deal_changed (future)
│ event_key TEXT                     │
│ player_id UUID FK                  │
│ player_room_account_id UUID FK NULL │
│ rakeback_wallet_id UUID FK NULL    │
│ destination_key TEXT               │
│ source_payload_snapshot JSONB      │
│ draft_payload JSONB                │  editable fields
│ draft_revision INTEGER             │
│ review_status TEXT                 │  pending / reviewing / snoozed /
│                                    │  approved / cancelled
│ snoozed_until TIMESTAMPTZ NULL     │
│ preferred_reviewer_id UUID FK NULL │
│ priority_until TIMESTAMPTZ NULL    │
│ claimed_by UUID FK NULL            │
│ claim_until TIMESTAMPTZ NULL       │
│ approved_by / approved_at          │
│ cancelled_by / cancelled_at        │
│ message_text_snapshot TEXT NULL    │  frozen only on Send
│ created_by / created_at            │
│ updated_at                         │
└────────────────────────────────────┘

UNIQUE(destination_key, event_key)
```

Человеческий workflow отделён от технической доставки:

```text
telegram_outbox
┌────────────────────────────────────┐
│ id UUID PK                         │
│ task_id UUID FK UNIQUE             │
│ delivery_status TEXT               │  queued / sending / sent /
│                                    │  retry / delivery_unknown / dead
│ attempt_count INTEGER              │
│ next_attempt_at TIMESTAMPTZ NULL   │
│ lease_until TIMESTAMPTZ NULL       │
│ telegram_message_id TEXT NULL      │
│ last_error TEXT NULL               │
│ created_at / sent_at               │
└────────────────────────────────────┘
```

Включение аккаунтов в пакет фиксируется отдельно:

```text
new_account_notification_items
┌───────────────────────────────────┐
│ task_id UUID FK                   │
│ player_room_account_id UUID FK    │
│ destination_key TEXT              │
│ item_status TEXT                  │  pending / sent / cancelled
│ created_at TIMESTAMPTZ            │
└───────────────────────────────────┘

UNIQUE(player_room_account_id, destination_key)
```

Серверная функция блокирует запись игрока, выбирает все его подтверждённые аккаунты без такой отметки и создаёт одну `telegram_notification_task` вместе со всеми `new_account_notification_items` в одной транзакции. Если готовых аккаунтов нет, пустой черновик не создаётся. Уникальность items означает, что два сотрудника, повторный `ok`, первое сохранение кошелька и повторная обработка события не поместят один аккаунт в два черновика.

Первое сохранение основного рейкбек-кошелька запускает эту проверку для всех уже подтверждённых аккаунтов игрока. Если кошелёк существовал раньше, переход нового аккаунта в `ok` запускает тот же процесс. Уже отправленные или явно отменённые аккаунты повторно как `new_accounts` не появляются без отдельного восстановления отменённой задачи. В `telegram_notification_tasks.rakeback_wallet_id` сохраняется кошелёк, использованный при подготовке черновика; отдельное сообщение о последующей смене кошелька относится к другому `event_type`.

#### Предпросмотр, редактирование и перенос

У черновика нет прямого перехода к отправке без участия сотрудника:

```text
pending
   │ сотрудник открывает preview
   ▼
reviewing
   ├── сохранить изменения ────────────────┐
   │                                      │
   ├── Отложить ──> snoozed ── срок ──> pending
   ├── Отменить ──> cancelled
   └── Отправить ─> approved ─> telegram_outbox.queued
                                          │
                                          ▼
                              sending ─> sent
                                 ├── retry
                                 ├── delivery_unknown
                                 └── dead
```

Предпросмотр строится из `draft_payload` и показывает отдельные редактируемые поля, а рядом — итоговый текст. Для `new_accounts` это блоки аккаунтов, идентификаторы, сделки, subaffiliate, основной рейкбек-кошелёк и контакты; для `rakeback_wallet_changed` — список аккаунтов и новый кошелёк. Получатель `operations_chat` не редактируется.

Редактирование бизнес-полей в предпросмотре не создаёт отдельную, расходящуюся с БД версию сообщения. Username и идентификаторы сохраняются в `player_room_accounts`, сделка — через назначение сделки аккаунту, кошелёк — через команду управления `player_wallets` с сохранением истории, контакты — в `player_contacts`. Для этих изменений применяются те же серверные проверки, аудит и контроль ревизии, что и при редактировании карточки игрока. После успешного сохранения сервер обновляет `source_payload_snapshot`, перестраивает `draft_payload` и увеличивает `draft_revision`.

Действия:
* `Отправить` — основной одношаговый сценарий: повторно валидирует обязательные поля и ревизии, при наличии правок атомарно сохраняет их в основные сущности БД, заново формирует и фиксирует `message_text_snapshot`, сохраняет автора, создаёт единственную запись `telegram_outbox` и только после этого переводит задачу в `approved`; отдельное предварительное нажатие `Сохранить изменения` не требуется;
* `Сохранить изменения` применяет те же проверки и сохраняет исправления в основные сущности БД, обновляет снимки и ревизию черновика, но не создаёт запись в `telegram_outbox`; после этого сообщение можно отправить, отложить или отменить;
* `Отменить` окончательно переводит текущую задачу и её items в `cancelled`, ничего не отправляет и сохраняет автора/время; отменённую задачу можно восстановить отдельным действием из истории, но система не создаёт её заново сама;
* `Отложить` по умолчанию устанавливает серверное `now() + 15 minutes`; сотрудник также может выбрать другую длительность или точные дату и время;
* окончание переноса только возвращает задачу в `pending` и повторно показывает уведомление; автоматического перехода в `approved` или `queued` не существует;
* закрытие приложения не отменяет и не отправляет задачу: `snoozed_until` хранится в Supabase как UTC, а интерфейс показывает время в локальной зоне сотрудника;
* если приложение было выключено в момент окончания переноса, просроченный черновик появляется при следующем подключении.

Для нескольких сотрудников сервер хранит `preferred_reviewer_id`. При создании задачи им становится сотрудник, чьё действие выполнило последнее недостающее условие: подтвердило привязку либо сохранило основной рейкбек-кошелёк. Если другой сотрудник затем явно сохраняет изменения или откладывает задачу, приоритет переходит к нему; один лишь просмотр приоритет не меняет. После окончания переноса уведомление сначала получает этот сотрудник. Если он офлайн, задача сразу становится доступна всем; если онлайн, но не реагирует до `priority_until`, она также возвращается в общую очередь. В общей очереди показывается, кому задача была назначена в первую очередь.

Если перед `Отложить` или `Отменить` остались несохранённые правки, приложение не угадывает намерение сотрудника: оно предлагает сохранить исправления, отбросить их либо вернуться к предпросмотру. Это подтверждение не показывается, когда поля не менялись.

Чтобы два сотрудника не отправили или не изменили один черновик одновременно, первый открывший получает короткую серверную блокировку (`claimed_by`, `claim_until`). Пока предпросмотр открыт, приложение продлевает её. Каждое изменение требует ожидаемую `draft_revision` и увеличивает ревизию; устаревшая форма получает понятное сообщение, загружает актуальные данные и ничего не отправляет. После истечения блокировки задача снова доступна другому сотруднику.

Если исходные данные аккаунта, сделки или кошелька изменились во время просмотра, `Отправить` останавливается и предлагает обновить предпросмотр. Worker забирает только подтверждённые записи `telegram_outbox`; `pending`, `reviewing` и `snoozed` он не видит.

#### Формат сообщения в рабочий чат

В отличие от ответа игроку, внутренний Telegram-анонс формируется из типизированных данных. Блок аккаунта повторяется для каждого готового аккаунта игрока, а кошелёк и контакты выводятся один раз в конце:

```text
Account {room_name}
{room_username}[ / {room_player_id}]
Deal: {deal_text_snapshot}
[Referred by subaff: {subaffiliate_name}]

[Account {room_name}
{room_username}[ / {room_player_id}]
Deal: {deal_text_snapshot}
[Referred by subaff: {subaffiliate_name}]]

...

{rakeback_wallet_currency} {rakeback_wallet_network}
{rakeback_wallet_address}
[{contact_method}: {primary_contact}]
```

Правила формирования:
* в строке аккаунта выводятся все имеющиеся идентификаторы без пустых разделителей;
* `deal_text_snapshot` отдельно фиксируется для каждого аккаунта на момент его подтверждения и не меняется при последующем редактировании справочника;
* данные кошелька берутся только из активного основного `rakeback_payout` и сохраняются снимком;
* `Referred by subaff` относится к конкретному аккаунту, а контакты — к игроку и выводятся один раз после кошелька;
* перед созданием задания обязательны рум, хотя бы один идентификатор аккаунта, сделка и полный основной рейкбек-кошелёк; неполные данные показываются сотруднику и не отправляются молча;
* в `message_text_snapshot` сохраняется точный готовый текст, который Worker передаст Telegram.

Обезличенный пример пакета из двух аккаунтов:

```text
Account CoinPoker
player_nick_one / PLAYER_ID
Deal: rake chase
Referred by subaff: subaffiliate_name

Account ShenPoker
player_nick_two
Deal: 25% Net Revenue

USDT TRC20
TExample...Address

Telegram: @player_contact
```

#### Смена основного рейкбек-кошелька

Черновик этого типа создаётся только при постоянной замене уже существующего основного `rakeback_payout`. В той же транзакции старый кошелёк архивируется, новый становится основным, а для игрока создаётся одна задача `pending`, требующая предпросмотра. Первое сохранение кошелька и действие `Использовать один раз без сохранения` сюда не попадают.

```text
event_type = rakeback_wallet_changed
event_key = rakeback_wallet_changed:{new_wallet_id}
source_payload_snapshot
  ├── player identity
  ├── affected account snapshots[]
  └── new wallet snapshot
```

Старый кошелёк сохраняется в истории `player_wallets`, но в текст рабочего сообщения не включается. В список попадают снимки затронутых аккаунтов: название рума, все имеющиеся идентификаторы и необязательная поясняющая заметка аккаунта.

```text
Смена кошелька
{room_name}  {room_username}[ / {room_player_id}][ / {email}] [({account_note})]
{room_name}  {room_username}[ / {room_player_id}][ / {email}] [({account_note})]
...

Новый кошелек
{rakeback_wallet_currency} {rakeback_wallet_network}
{rakeback_wallet_address}
```

Обезличенный пример:

```text
Смена кошелька
Americas Cardroom  player_one / player@example.com
Nexa  player_two / 1234567 / player@example.com
BCPoker  320000
Americas Cardroom  related_account / related@example.com (related account note)

Новый кошелек
USDT BEP20
0xABCD...1234
```

#### Будущая структурированная смена сделки аккаунта

Текущая сделка аккаунта не должна перезаписываться без истории. Для неё используется версионируемое назначение:

```text
player_room_account_deals
┌─────────────────────────────────┐
│ id UUID PK                      │
│ player_room_account_id UUID FK  │
│ room_deal_id UUID FK NULL       │
│ deal_text_snapshot TEXT         │
│ status TEXT                     │  active / superseded
│ effective_from / effective_to   │
│ changed_by UUID FK              │
└─────────────────────────────────┘
```

Первоначальная сделка создаёт первую активную запись. При изменении прежняя запись закрывается, а новая становится активной. В первой реализации сотрудник при необходимости сообщает об изменении непосредственно в Telegram; отдельная автоматизация `deal_changed` откладывается.

```text
future event_type = deal_changed
future event_key = deal_changed:{new_account_deal_id}
```

Telegram-бот работает только на сервере: токен бота и ID рабочего чата не помещаются в Electron и не передаются обычному пользователю. Актуальность исходных данных проверяется атомарно при нажатии `Отправить`; после создания `telegram_outbox` Worker не пересобирает и не меняет утверждённое сообщение, а отправляет точный `message_text_snapshot`. Последующее изменение аккаунта или кошелька является новым бизнес-событием и не переписывает уже подтверждённую отправку.

Telegram Bot API возвращает ID сообщения после успешной отправки, но `sendMessage` не предоставляет ключ идемпотентности. Поэтому при обрыве соединения после принятия сообщения Telegram нельзя одновременно гарантировать отсутствие и пропусков, и дублей. Неоднозначный результат помечается `delivery_unknown` и показывается оператору для ручной проверки, а не отправляется автоматически второй раз.

## Планируемая серверная версия: аутентификация сотрудников

Для будущей версии с общей базой Supabase сотрудник входит через рабочий Google-аккаунт. Приложение не хранит пароли и не реализует собственное восстановление пароля: аутентификацией и подтверждением адреса управляют Google Workspace и Supabase Auth.

Планируемые правила доступа:
* Google OAuth используется только как подтверждение личности; доступ к данным дополнительно контролируется внутри Transactioner.
* Рабочие адреса обслуживаются Google Workspace и используют собственный корпоративный домен, а не общий домен `gmail.com`.
* Точное значение разрешённого домена хранится только в серверной конфигурации или защищённой таблице политик доступа; клиент не является доверенным источником этой настройки.
* Одного совпадения домена почты недостаточно для доступа. Рабочий адрес должен быть заранее добавлен администратором в список разрешений.
* Заблокированный или неактивный сотрудник не получает доступ, даже если его Google-аккаунт продолжает существовать.
* Роли первой версии: `admin` и `operator`. Роль `viewer` не создаётся до появления реального сценария доступа только для чтения.
* `admin` управляет приглашениями, блокировкой сотрудников, ролями, системными настройками и имеет доступ к журналу аудита.
* `operator` выполняет ежедневную работу с игроками, аккаунтами, кошельками, генерацией шаблонов и редактированием общего справочника, но не управляет сотрудниками и политиками доступа.
* Роль хранится как явное значение в профиле сотрудника, а проверки доступа выполняются на уровне Supabase RLS и серверных функций, а не только скрытием кнопок в интерфейсе.
* Все изменения чувствительных данных должны сохранять автора через `user_id`, а административные изменения должны попадать в журнал аудита.
* В десктопное приложение нельзя помещать Supabase `service_role` key или другие серверные секреты.

Supabase создает и обслуживает системную таблицу `auth.users`. В прикладной схеме Transactioner нужна связанная сущность сотрудника:

```text
auth.users                         employee_profiles
┌──────────────────────────┐       ┌────────────────────────────┐
│ id UUID PK               │ 1──1  │ user_id UUID PK/FK         │
│ email                    │       │ work_email TEXT UNIQUE      │
│ email_confirmed_at       │       │ display_name TEXT           │
│ provider = google        │       │ role TEXT                   │
│ last_sign_in_at          │       │ status TEXT                 │
└──────────────────────────┘       │ created_at / updated_at     │
                                   └──────────────┬─────────────┘
                                                  │ 1
                                                  │
                                                  │ N
                                   ┌──────────────▼─────────────┐
                                   │ audit_log                  │
                                   │ actor_user_id UUID FK      │
                                   │ entity_type / entity_id    │
                                   │ action / changes / date    │
                                   └────────────────────────────┘
```

`auth.users.id` является стабильной идентичностью сотрудника. Рабочая почта нужна для отображения и контроля доступа, но не должна использоваться как внешний ключ: адрес может измениться. Таблицы с изменяемыми бизнес-данными в будущей схеме получают поля `created_by` и `updated_by`, ссылающиеся на `employee_profiles.user_id`.

Предварительное разрешение хранится отдельно от профиля уже вошедшего сотрудника:

```text
employee_invitations
┌──────────────────────────────┐
│ id UUID PK                   │
│ work_email CITEXT UNIQUE     │
│ initial_role TEXT            │
│ status TEXT                  │  pending / accepted / cancelled
│ invited_by UUID FK           │
│ invited_at TIMESTAMPTZ       │
│ accepted_at TIMESTAMPTZ      │
│ cancelled_at TIMESTAMPTZ     │
└──────────────┬───────────────┘
               │ 1
               │
               │ 0..1
               ▼
employee_profiles
┌──────────────────────────────┐
│ user_id UUID PK/FK           │  -> auth.users.id
│ invitation_id UUID UNIQUE    │
│ work_email CITEXT UNIQUE     │
│ display_name TEXT            │
│ role TEXT                    │
│ status TEXT                  │
└──────────────────────────────┘
```

Первый вход связывает подтверждённый Google email с ожидающим `employee_invitations`, создаёт `employee_profiles` и помечает приглашение принятым. После этого роль и текущий статус доступа хранятся только в `employee_profiles`, чтобы не было двух конфликтующих источников прав. Отсутствующее, отменённое или не совпадающее приглашение не даёт доступа к прикладным таблицам. Отзыв доступа переводит профиль в неактивный статус и блокирует новые запросы через политики Supabase RLS, но записи `audit_log` и ссылки `created_by` сохраняются.

Открытые решения перед реализацией:
* политика завершения активных сессий после блокировки сотрудника.

## Планируемая функция: справочник по румам
Цель: быстро отвечать на частые вопросы сотрудников и игроков без ручного поиска по чатам/документам.

Приоритет реализации:
1. **MVP 1 — депозитные кошельки:** быстро выбрать рум, увидеть платежные методы и список кошельков. Должна быть возможность скопировать все кошельки/методы сразу или выделить одну строку и скопировать только ее.
2. **MVP 2 — сделка в руме:** быстро выбрать рум, выбрать язык RU/EN, увидеть текст сделки. Должна быть возможность скопировать шаблон целиком или выделить/скопировать короткое описание.
3. **Следующий этап — проверка по стране:** при вопросе о сделке добавить выбор страны. Приложение должно либо показать подходящий шаблон агентской/прямой сделки, либо сообщить, что рум недоступен в выбранной стране. Если доступны обе сделки, сотрудник выбирает нужный тип.
4. **Следующий этап — переключение языка:** в каждом сообщении справочника должна быть возможность сменить язык, и текст автоматически меняется на соответствующую RU/EN версию.

Источник данных:
* Текущая база знаний хранится как структурированные Google Docs по каждому руму/сети и сводные Google Sheets, а не как реляционная БД.
* На первом этапе приложение не подключается к ИИ или Google Docs напрямую. Оно хранит локальную нормализованную выжимку в SQLite/JSON, которую можно наполнить вручную или импортом.
* На ближайшем этапе приложение хранит только операционную выжимку для частых задач: кошельки, сделки RU/EN и доступность по странам. Полные большие описания румов остаются внешним источником и не переносятся целиком в приложение.

Основные типы информации:
* **Сделки по румам:** короткое описание, подробное описание, язык шаблона, ссылка на регистрацию.
* **Варианты сделки внутри одного рума:** разделение есть не у всех румов. На текущий момент: Champion Poker имеет Direct и Agent с разными ссылками/инструкциями/условиями кассы; Nexa рассматривается как агентская сделка; RedStar имеет прямую и агентскую сделку, но общий шаблон.
* **Доступность по странам:** если информация есть, хранить доступные/недоступные страны, требования к VPN, допустимые страны регистрации и особые инструкции.
* **Кошельки и методы депозитов:** монета, сеть, адрес, memo/tag при наличии, комиссия, комментарий, активность, дата последней проверки/актуальности.
* **Методы вывода через нас:** доступные сети/монеты, комиссии и ограничения.
* **Промокоды и трекеры:** хранить отдельно от регистрационной ссылки, так как в некоторых сетях они зависят от языка/страны.

Сегментация:
* **Язык:** RU/EN версии коротких описаний и шаблонов сделки.
* **Тип кассы/сделки:** Direct, Agent или общий шаблон без разделения.
* **Страна/регион:** доступность рума, бонусы, требования к VPN, отдельные ссылки для регионов.
* **Тип игрока/особые условия:** если влияет на выплату или возможность сделки, хранить как заметку/предупреждение.

UX-идея:
* Отдельный раздел в боковом меню "Инфо по румам".
* Первый экран справочника должен быть рабочим инструментом, а не общей страницей: быстрый выбор сценария "Кошельки" или "Сделка".
* Для сценария "Кошельки": рум -> платежные методы -> список кошельков/сетей/комиссий -> копирование всех строк или одной выбранной строки.
* Для сценария "Сделка": рум -> язык -> текст сделки -> копирование полного шаблона или короткого описания.
* В следующих версиях: поиск по названию рума, варианту сделки, стране, языку, сети/монете, промокоду и ключевым словам.
* Карточка рума с вкладками/блоками: "Сделка", "Регистрация", "Страны", "Депозиты/выводы", "FAQ", "Заметки".
* Кнопки копирования для короткого шаблона, полного шаблона, ссылки регистрации, промокода и кошелька.
* Для чувствительных данных вроде депозитных кошельков показывать дату последней проверки.
* Если кошелек помечен как неактуальный или дата актуальности устарела, показывать предупреждение перед копированием.
* Админка справочника должна редактировать локальную SQLite-БД: добавлять румы, редактировать сделки и кошельки. Seed из приложения используется только для добавления отсутствующих стартовых записей и не должен перетирать ручные изменения после первого запуска.

Черновая модель данных для реализации:
* `room_profiles`: название рума, сеть/бренд, активность, краткое описание, заметки.
* `room_deals`: рум, тип сделки, язык, короткий текст, полный текст, регистрационная ссылка, промокод, требования к регистрации/VPN.
* `room_payment_methods`: рум, тип сделки, операция (депозит/вывод), метод, монета, сеть, комиссия, лимиты, комментарий.
* `room_wallets`: рум, тип сделки, монета, сеть, адрес, memo/tag, комментарий, активность, дата актуальности.
* `room_country_availability`: рум, страна/регион, статус (доступен/недоступен/нужен VPN/уточнить), комментарий, источник/дата.
* `room_faq_items`: рум, язык, вопрос, короткий ответ, полный ответ.

## Поля и Форматы шаблонов
Анализ предоставленных примеров показал следующие необходимые поля для каждого рума:

**1. RedStar**
