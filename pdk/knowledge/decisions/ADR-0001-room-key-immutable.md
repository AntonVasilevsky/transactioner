# ADR-0001: room_key неизменяем после создания рума

## Context

Все данные рума (сделки, платёжные методы, кошельки, страны, шаблоны ответа на привязку) связаны с `room_profiles` только текстом `room_key`. `saveRoomProfile` разрешает менять ключ существующего профиля, а форма рума пересчитывает ключ из названия — переименование рума молча отрывает его данные; seed затем воссоздаёт старый профиль. Проверено на временной БД (аудит: [`../notes/T-0004-schema-audit.md`](../notes/T-0004-schema-audit.md), риск 1). Затрагивает REQ-ROM-008, REQ-ROM-009, REQ-LNK-010.

## Decision

- `room_key` задаётся один раз при создании рума и далее не меняется. Название (`display_name`), сеть, заметка и активность остаются редактируемыми.
- Код: `saveRoomProfile` при обновлении по `id` отклоняет смену `room_key` с понятной ошибкой; форма рума не пересчитывает и не даёт редактировать ключ у существующего рума.
- БД: триггер `BEFORE UPDATE OF room_key ON room_profiles` с `RAISE(ABORT)` при изменении значения — страховка от будущих путей записи.
- Связь остаётся текстовой; FK и перестройка таблиц не вводятся.

## Alternatives considered

- **Каскадное переименование** — при смене ключа в одной транзакции обновлять `room_key` в 5 дочерних таблицах. Сохраняет гибкость, но ключ — внутренний идентификатор, менять его пользователю незачем; нужно ещё обновлять seed-совпадения, иначе seed воссоздаст старый рум. Отклонено как лишняя сложность; при реальной потребности добавляется отдельной явной операцией.
- **Целочисленный `room_id` FK во всех дочерних таблицах** — защита на уровне SQLite, но перестройка таблиц, перенос данных и переписывание IPC/renderer, завязанных на `room_key`. Выигрыш сверх неизменяемого ключа для локального этапа мал. Вернуться при проектировании общей версии.

## Consequences

- Переименование рума больше не теряет данные; триггер ловит ошибку любого будущего кода.
- Опечатку в ключе нового рума исправить через UI нельзя: создать рум заново и деактивировать ошибочный (данных у свежего рума ещё нет).
- Уже существующие расхождения (если ключ менялся раньше) этим не исправляются: реализация должна проверить наличие строк дочерних таблиц без профиля и сообщить о них, не удаляя.
- Пересмотреть при переходе к общей многопользовательской версии.
