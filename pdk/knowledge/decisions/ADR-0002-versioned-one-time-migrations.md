# ADR-0002: Версионированные одноразовые миграции и seed только для новой БД

## Context

`migrate()` при каждом запуске выполняет все шаги: seed стартовых данных (`ON CONFLICT DO NOTHING`), создание Deposit-методов из кошельков, удаление 5 устаревших комбинированных методов. Поэтому удалённые пользователем стартовые методы и методы, созданные из кошельков, возвращаются после перезапуска, а вручную созданный метод с совпадающим «устаревшим» ключом удаляется (проверено на временной БД; аудит [`../notes/T-0004-schema-audit.md`](../notes/T-0004-schema-audit.md), риск 2). Это нарушает REQ-ROM-009. `PRAGMA user_version` = 0, версий схемы нет; ежедневный backup не гарантирует свежую копию перед миграцией (риск 8). Затрагивает REQ-ROM-009, REQ-QLT-006 и constraint о сохранности БД при обновлении.

## Decision

- Версия схемы хранится в `PRAGMA user_version`. Миграции — упорядоченный список шагов; каждый выполняется один раз, в транзакции вместе с повышением `user_version`.
- Перед применением хотя бы одного ожидающего шага создаётся snapshot `before-migration` (существующий `createDatabaseSnapshotBackup`); провал snapshot останавливает миграцию (REQ-QLT-006).
- Стартовый seed применяется один раз — для БД без него. Новые справочные данные в будущих релизах поставляются как отдельные пронумерованные шаги, вставляющие конкретные строки один раз.
- Существующие эвристики (`migrateWalletsToPaymentMethods`, `cleanupLegacyCombinedPaymentMethods`, `cleanupCombinedDepositMethodsBackedByWallets`, сброс кошельков) становятся одноразовыми шагами: на существующей БД они выполнятся последний раз при переходе на версионирование и больше не повторятся.
- `CREATE TABLE/INDEX/TRIGGER IF NOT EXISTS` и `ADD COLUMN` для старых БД остаются базовым шагом.

## Alternatives considered

- **Мягкое удаление вместо физического** (`is_active = 0`) — запись остаётся, `DO NOTHING` её не воскрешает. Не закрывает случай изменения уникального ключа стартовой записи (seed добавит дубликат) и повторное удаление «устаревших» методов; к тому же правило hard delete vs inactive — открытый вопрос владельца. Может применяться дополнительно, но не заменяет решение.
- **Таблица «надгробий» удалённых стартовых ключей** — seed пропускает перечисленные ключи. Сохраняет перезапуск seed, но добавляет учёт каждого удаления и не решает изменение ключа. Сложнее при том же результате.
- **Оставить как есть** — удалённое продолжает возвращаться; противоречит REQ-ROM-009.

## Consequences

- Удаление и правка справочника переживают перезапуск и обновление.
- Новый релиз со справочными данными требует явного шага миграции, а не правки seed-массива; это нужно отразить в release workflow.
- Ошибка в шаге не оставляет БД в промежуточном состоянии: транзакция откатывается, есть snapshot.
- Нужны тесты: повторный запуск не возвращает удалённое; переход существующей БД с `user_version = 0`; провал шага откатывает версию.
