## Findings

- [minor] electron/database.ts:1568 — on an existing v0 DB, step 1 runs the seed and `migrateWalletsToPaymentMethods` once more. Rows deleted in the last session before the update therefore return once.
  Why: ADR-0002 says "seed only for a DB without it". The Acceptance allows "or once on an existing DB", so this is not a blocker. Other users' installs are affected; the owner's DB is already migrated.
  Fix: add a line to `USER_RELEASE_NOTES.txt` for the release ("items deleted before the update may reappear once — delete them again").
- [minor] electron/main.ts:276 — a failed snapshot shows "database needs manual cleanup".
  Why: that message is misleading for a backup failure (unwritable or permission-denied Documents folder). The user may think the DB is damaged.
  Fix: show a separate message for a backup failure ("could not create backup in <backupDir>, check folder access"), e.g. a dedicated error class.
- [minor] docs/room_knowledge_plan.md:184, pdk/knowledge/architecture.md:175–183 (draft), electron/roomKnowledgeSeed.ts header — they still say the seed runs on every start and that updates add new records. The ADR-0002 consequence "reflect in release workflow" is not done.
  Why: the next change to `roomKnowledgeSeed.ts` will silently never reach existing DBs.
  Fix: add a header comment in roomKnowledgeSeed.ts ("new reference data = new numbered step in migrationSteps") and update the docs. Propose an AGENTS.md line to the owner.
- [minor] electron/database.test.ts:1245 — the v0→v1 test asserts that only wallets and player accounts survive.
  Why: Acceptance 5 also lists methods, deals and templates.
  Fix: also assert that a user-created payment method, an edited deal and a link-verification template survive the transition.
- [nit] electron/database.ts:1555 — unversioned startup steps (ALTERs, `migrateLinkVerificationResponseTemplates`, the wallet reset guarded by app_settings) run before `runMigrations`, outside step 1's transaction.
  Why: if step 1 fails, those steps are not rolled back; the snapshot covers this. Behaviour is the same as before; the wallet reset is already one-time via its flag.
  Fix: none required.

Checked and fine: the wallet reset now runs before the seed, but the seed inserts no wallets (`wallets: []`, no wallet INSERT). The journal mode is the default (no WAL), so copying the file for the snapshot is consistent. Fresh DB → no hook call (test :1275). New tests 1–3 would fail on the old code because the seed and wallet→method steps re-ran on every start.
