[blocker] src/utils/roomMethodGroups.ts:195 — снятие галочки «Депозит» кладёт в план `walletDelete`, и после сохранения строка `room_wallets` удаляется.
  Why: решение владельца и Acceptance прямо требуют «снятие галочек не должно трогать room_wallets». Тест в roomMethodGroups.test.ts закрепляет обратное (`noDeposit.walletDelete` равен 9). По ADR-0003 кошелёк без метода допустим; в «Инфо по румам» он и так не показывается, пока у рума есть настроенные методы, так что хранить его безопасно.
  Consequence: оператор, снявший «Депозит» и подтвердивший диалог не глядя, теряет адрес депозитного кошелька рума; восстановление только вручную из снапшота before-room-edit.
  Fix: убрать `walletDelete` из ветки снятия «Депозит» (удаление только явной кнопкой «Удалить кошелек»), поправить тест и добавить тест на уровне БД «после снятия галочки адреса не изменились». Либо владелец подтверждает текущее поведение и текст задачи обновляется.

[blocker] electron/database.ts:1189 — сохранение без id ищет строку той же монеты+сети и обновляет её; `planRoomMethodGroupSave` (src/utils/roomMethodGroups.ts:147) при draft без `groupKey` существующую группу не проверяет.
  Why: «Новый» → USDT TRC20, когда такая группа уже есть, без вопроса записывает в её строки пустые `fee_text`/`limits_text`, `sort_order` 0 и `is_active` из формы; при другом адресе `saveRoomWallet` без id вставляет второй кошелёк рядом со старым (ON CONFLICT только при полном совпадении адреса). Тест «updates the existing coin + network row» закрепляет перезапись как норму.
  Consequence: игроку уходит список с устаревшим адресом рядом с новым, а предупреждение о минимуме пропадает без ведома оператора.
  Fix: в `planRoomMethodGroupSave` (или в `saveMethodGroup`) при draft без `groupKey` и существующей группе с тем же `roomMethodGroupKey` возвращать error «Метод USDT TRC20 уже есть, откройте его для редактирования» либо открывать существующую группу; тест на этот случай.

[blocker] src/utils/roomMethodGroups.ts:82 — активность группы считается как «хотя бы одна строка активна», и при сохранении (строка 168) этот флаг записывается во все строки обеих операций.
  Why: project.md «Critical» называет `room_payment_methods.is_active` полем, решающим канал оплаты; `payableRoomKeysForOperation` (src/utils/roomAccountOptions.ts:36) по нему решает, в каких румах доступен вывод.   Fix: хранить `is_active` по операции в `RoomMethodOperationDraft` (две галочки или галочка внутри блока операции) либо не менять флаг строки, если оператор не трогал «Метод активен»; тест: депозит активен, вывод нет → после сохранения вывод остаётся неактивным.
